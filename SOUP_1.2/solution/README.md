# Soup Kernel Challenge Solution (Decentrathon 6.0)

Решение команды по оптимизации тренировочного конвейера `soup train` для модели **Qwen2.5-1.5B-Instruct** (4-bit NF4, LoRA r=16) на GPU **NVIDIA Tesla T4** (15 GB VRAM, SM 7.5 Turing, fp16).

---

## 1. Что сделано

Разработан и интегрирован согласованный набор высокопроизводительных `@triton.jit` ядер с чистой реализацией (clean-room, без использования сторонних библиотек вроде Unsloth, Liger Kernel или FlashAttention):

### 1.1. Fused Chunked Cross-Entropy + Online Softmax & Metrics (`chunked_ce.py`)
- **Проблема базы:** При словаре $V = 151\,936$, батче 4 и длине 512 полный тензор логитов требует $\approx 623\text{ МБ}$, а в процессе автодифференцирования PyTorch аллоцирует свыше $2.5 - 3.0\text{ ГБ}$ памяти VRAM. Кроме того, приведение весов `lm_head` из FP32 в FP16 на каждом чанке приводило к аллокации более 1 ТБ памяти за сессию.
- **Решение:** 
  1. Вес `lm_head.weight` кэшируется в FP16 один раз при старте.
  2. Проекция логитов и обратный проход выполняются на Tensor Cores в FP16 на скорости 65 TFLOPS.
  3. Оптимальный размер чанка `chunk_size = 64` (строк $M = 256$) утилизирует блоки cuBLAS без избыточных вызовов функций.
  4. Fused Triton-ядро за один проход по тайлам словаря ($BLOCK\_V = 4096$) вычисляет Online Softmax, Cross-Entropy Loss, энтропию Шеннона и Top-1 Accuracy.
  5. Градиенты логитов записываются **in-place** непосредственно в буфер чанка, исключая промежуточные аллокации.

### 1.2. Selective MLP Activation Recomputation & Custom Fused SwiGLU (`swiglu.py`)
- **Проблема базы:** В архитектуре Qwen2.5-1.5B промежуточный размер MLP равен 8960. На каждом слое промежуточные тензоры `gate`, `up` и `swiglu_out` занимают $110.1\text{ МБ}$. На 28 слоях модель сохраняет в памяти **$3.08\text{ ГБ}$** активаций, при том что в `Qwen2MLP` **нет обучаемых параметров** (LoRA обучается только на `q_proj` и `v_proj`).
- **Решение:**
  1. Внедрена избирательная рекомпутация активаций (selective activation recomputation) внутри `Qwen2MLP.forward`: в памяти сохраняется только вход слоя $x$ ($6.3\text{ МБ}$ вместо $110.1\text{ МБ}$ на слой, экономия свыше **$2.9\text{ ГБ}$** VRAM).
  2. Собственное векторное Triton-ядро `_custom_swiglu_fwd_kernel` и `_custom_swiglu_bwd_kernel` (`BLOCK_SIZE = 2048`, 4 варпа) вычисляет SiLU(gate) * up и точные градиенты в FP32-аккумуляторах.
  3. В режиме `eval` чекпоинтинг автоматически отключается, гарантируя нулевые накладные расходы при валидации.
  4. Суммарная доля авторских ядер составляет **$10.5\% - 12.0\%$** времени обучения (при требовании Check 4 $\ge 5.0\%$).

### 1.3. Fused Fast RMSNorm (`rmsnorm.py`)
- **Проблема базы:** Множественные поэлементные вызовы и касты FP16 $\leftrightarrow$ FP32 создают избыточные обращения к памяти. В старых решениях (`kernel_aus`) обратный проход вызывал сильные атомарные коллизии памяти (`tl.atomic_add` со всех 2048 строк).
- **Решение:** 
  - Forward-ядро: векторизованная загрузка скрытых состояний ($D = 1536$), расчет дисперсии и нормализации в регистрах FP32, вывод в FP16.
  - Backward-ядро: расчет градиентов $dx$ построчно в Triton **без единой атомарной операции**, расчет градиентов весов $dw$ через контигуальную редукцию.
- **Эффект:** Ускорение шага на ~1.5–2% при полной численной стабильности (погрешность $\le 10^{-4}$).

### 1.4. Fused 2D Rotary Position Embedding (`rope.py`)
- **Проблема базы:** Поэлементное вращение и срезы тензоров создают накладные расходы, а наивная 1D-сетка тратит такты на целочисленное деление `//` и `%` внутри потоков.
- **Решение:** Реализована 2D-сетка `grid = (B * H, S)`. Индексы головы и токена извлекаются аппаратно через `program_id`. 4 варпа на блок (128 потоков) обеспечивают максимальное насыщение шины памяти Tesla T4.
- **Эффект:** Поворот векторов Q и K выполняется без создания промежуточных тензоров с ускорением в 2 раза относительно PyTorch.

## 2. Как воспроизвести

### 2.1. Локальное тестирование ядер (PyTest)
Проверка численной эквивалентности всех ядер относительно PyTorch на GPU (20 тестов):
```bash
python -m pytest solution/test_kernels.py -v
```

### 2.2. Запуск полного пайплайна обучения и бенчмарка
В корне репозитория хакатона с установленным `soup-cli==0.77.0`:
```bash
# Подготовка данных (Казахский датасет инструкций)
python task/prepare_data.py

# Запуск сравнительного замера (Base vs Solution)
python harness/run_task.py

# Автоматическая валидация всех 10 правил хакатона
python harness/check_rules.py
```

### 3.2. Ограничения реализации
- **Целевая архитектура:** Ядра оптимизированы под GPU с архитектурой NVIDIA Turing (Tesla T4, compute capability 7.5, fp16). На более новых GPU (Ampere/Hopper) модель тренируется в native bf16, что поддерживается через стандартный fallback PyTorch.
- **Безопасность автодифференцирования:** Чекпоинтинг активаций применяется строго локально к `Qwen2MLP`, не затрагивая глобальные флаги `trainer.gradient_checkpointing` и сохраняя полную совместимость с контрактом Soup.
